Sessions expire 24h after sign-in

acme/dashboard #4821 · feat/session-expiry · 34 files (+612 −188) · 5 chapters

Signing in to the dashboard used to hand you a session that lived forever. This PR gives every session a 24-hour clock, teaches the browser to tell "your session ran out" apart from "you were never signed in", and deletes the dead rows on a schedule. Anyone signed in when this deploys gets logged out.

What's in here

Scope is deliberately narrow. It does not touch how you sign in (password, Okta SSO), it adds no refresh tokens, and it adds no "remember me" — those stay exactly as they are.

New behaviour

  • Sessions carry an expiresAt, stamped at creation 24 hours out. validateSession() refuses anything past it.
  • Time is read through a small SessionClock seam instead of Date.now(), so tests can fast-forward a day in a millisecond.
  • An expired session gets 401 plus an X-Session-Expired: 1 header, so the frontend can tell "ran out" apart from "never signed in".
  • The web app reacts once, centrally: a toast, then a redirect to /login?reason=expired.
  • A worker job sweeps expired rows out of sessions every 15 minutes.

Plumbing

  • SessionClock threaded through three createSession() call sites, four validateSession() ones, and the API's DI container.
  • CORS now exposes X-Session-Expired — without that the browser hides it from JS.

Worth knowing

  • The TTL is measured from createdAt, not lastSeenAt. DASH-2274 originally asked for a sliding window where every request pushes the deadline out. That got dropped. As written, someone actively clicking around is logged out 24h after signing in, mid-session. Sliding renewal is tracked separately in DASH-2318.
  • Everyone gets logged out on deploy. The migration backfills existing rows with created_at + interval '24 hours'. There are ~1.4M rows and the median one is months old, so they expire the instant the column exists. Intentional, but user-visible.
  • Open streams are not killed. SSE and the dashboard websocket validate once, at connect. An expired session dies on the next reconnect — at most 60s for SSE, up to 5 minutes for the socket. DASH-2274 scopes the TTL to request authentication only.
  • The clock seam stops at packages/auth and the sweeper. Everything else still calls Date.now(). Half-threaded on purpose.

How this part of the system works

Three places in this monorepo care about sessions, and the change touches all three.

packages/auth is the domain layer. It owns two functions and no HTTP: createSession() writes a row and returns a raw token, validateSession() takes a raw token and tells you whose it is. It never touches the network and has no idea what a cookie is. Session rules change here.

services/api is a Fastify app. Its authenticate plugin runs as an onRequest hook on every route under /api/v1, pulls the acme_session cookie, hands the token to validateSession(), and either attaches request.currentUser or throws. Every route trusts that plugin and never re-checks.

apps/web is the React dashboard. Every network call goes through one wrapper, apiFetch(). Nothing calls fetch() directly — which is why one change in that wrapper catches expiry app-wide.

apps/web  ──apiFetch()──▶  services/api  ──authenticate──▶  packages/auth
                                                             │ validateSession()
                                                             ▼
                                                      packages/db  (sessions)
                                                             ▲

Start here: packages/auth/src/session.ts. It is the only file where the new rule actually lives. Everything else in this PR either feeds it a clock, reacts to what it returns, or cleans up after it.

Sessions get a 24-hour deadline

business logic

Before this PR a session row had a createdAt, a lastSeenAt and a nullable revokedAt. revokedAt is only ever set by an explicit logout or an admin killing a session. Nothing else could end a session, so a cookie lifted off a laptop that got wiped in March still worked in August.

This chapter adds the deadline. Every new session gets an expiresAt, stamped at creation 24 hours after createdAt. validateSession() grows a third failure mode next to "no such session" and "revoked": "expired". And because a rule about time is untestable when the code reads the wall clock, time now arrives as an argument — a SessionClock.

One detail to pin down before the code: the deadline is anchored to createdAt. Not lastSeenAt, which the table already tracks and bumps on every request. So this is a hard stop from sign-in, not an idle timeout.

  • New expiresAt column, plus a partial index for the sweeper
  • New SessionClock seam and systemClock
  • SESSION_TTL_MS = 24h, alone in its own file
  • createSession() stamps the deadline; validateSession() enforces it
  • New 'expired' arm on SessionResult
  • TestClock with advance(), and tests that fast-forward a day
Before After

Then the rule. Who calls this. Grepping outside the diff, createSession() has exactly three callers — routes/auth/login.ts (password), routes/auth/sso-callback.ts (Okta), and routes/admin/impersonate.ts (support staff impersonating a customer). That third one is worth noticing: impersonation sessions were the longest-lived rows in the table, and they now die in 24h with everything else. validateSession() has four callers, and they are the next chapter.

Telling "expired" apart from "never signed in"

business logic

Here is the problem the frontend had. The API's answer to "I have no valid session" was a bare 401, for every reason. So the web app could not tell two very different people apart: someone who is not logged in at all, and someone who was logged in, is mid-task, and just aged out. Both got the same silent bounce to /login, which reads as a bug — you were typing, and then you weren't.

This chapter makes them distinguishable. The status code does not change, so nothing that depends on 401 breaks. Instead the expired case carries a response header, X-Session-Expired: 1. A header rather than a body field is deliberate: apiFetch() can check it without reading and parsing the body, which matters because some 401s come back on requests whose bodies the caller streams.

  • authenticate maps reason to a response: expired → 401 + header + { error: 'session_expired' }
  • X-Session-Expired added to CORS exposedHeaders
  • apiFetch() detects it once, centrally, and fires a callback
  • New SessionExpiryBoundary shows one toast and redirects
  • Login page reads reason=expired and explains itself

Start at the plugin, because every route depends on it. Before this change it did if (!result.ok) throw unauthorized() — one branch for every failure. Now it switches on reason. This is the one file the new union member broke at compile time: nothing else in the repo matches SessionResult exhaustively, so nothing else had to change.

Then the UI. SessionExpiryBoundary wraps the authed layout. The handled ref is the whole point of the component: a dashboard page fires six or seven parallel requests, they all come back 401 at once, and without the guard you get seven toasts and seven navigations.

+export function SessionExpiryBoundary({ children }: { children: React.ReactNode }) {
+  const router = useRouter();
+  const handled = useRef(false);
+
+  useEffect(() => {
+    setSessionExpiredHandler(() => {

+      handled.current = true;
+      toast.info('Your session expired. Please sign in again.');

+    });
+    return () => setSessionExpiredHandler(() => {});
+  }, [router]);
+
+  return <>{children}</>;
+}

Who else calls validateSession(). Three call sites outside the plugin, none of them changed, and none of them read reason — so only the REST path produces the header. routes/events/stream.ts (SSE) and ws/upgrade.ts (live dashboard tiles) validate at connect only, so an expired session survives until the client reconnects. services/worker/src/http/preview-link.ts reuses dashboard sessions for signed preview links. Those links now stop working 24h after their owner signed in, even though a preview link carries its own separate expiry. DASH-2274 does not mention preview links.

Expired rows get deleted, not just ignored

business logic

An expired session still exists as a row. validateSession() refuses it, so it is harmless — but the table already has 1.4M rows and gains roughly 40k a day, and after the backfill nearly all of them are dead weight sitting in the index the API hits on every single request.

The job lives in services/worker, the existing cron host — it already runs expire-invites and rotate-api-keys on the same scheduler, so this is a fourth entry in a list rather than new infrastructure. It deletes in bounded batches and loops, because one DELETE covering a million rows takes a lock nobody wants during business hours.

  • Batched DELETE, 1000 rows at a time, capped at 50 batches per run
  • Registered on a */15 * * * * cron beside the other worker jobs
  • Emits sessions_swept_total so the Grafana panel shows the table draining
services/worker/src/jobs/sweep-expired-sessions.ts (new)
+export async function sweepExpiredSessions(clock: SessionClock = systemClock): Promise<number> {
+  const now = clock.now();
+  let deleted = 0;
+
+  for (let batch = 0; batch < MAX_BATCHES_PER_RUN; batch++) {
+    const rows = await db
+      .delete(sessions)
+      .where(and(isNull(sessions.revokedAt), lte(sessions.expiresAt, now)))
+      .limit(BATCH_SIZE)
+      .returning({ id: sessions.id });
+
+    deleted += rows.length;
+    if (rows.length < BATCH_SIZE) break;
+  }
+
+  metrics.counter('sessions_swept_total').inc(deleted);
+  return deleted;
+}

The ceiling is 50 × 1000 rows per run, four runs an hour, so the 1.4M-row backlog takes roughly seven hours to clear after deploy. That is what the Grafana panel linked at the top is for — the table size should visibly fall, then flatten.

The where clause is exactly what sessions_expires_at_idx from Chapter 1 indexes, including the revoked_at is null predicate. The index and the query were written as a pair; changing one without the other turns this into a sequential scan over the whole table.

Registration adds lockTtlMs: 10 * 60 * 1000 alongside the cron. That is the scheduler's existing advisory-lock timeout — worker runs three replicas, and without it two of them could sweep at once. Ten minutes is generous for a run that takes seconds, and it is deliberately shorter than the 15-minute cron so a crashed run does not block the next one forever.

Threading the clock to the call sites

mechanical

Chapter 1 made now an argument. This is the consequence: the same optional parameter added at seven call sites, plus a TestClock helper. There is no decision in here — every edit is the same shape, and all of them pass systemClock by default, so nothing outside tests changes behaviour.

services/api/src/routes/auth/login.ts:38 — and six more exactly like it
-    const { token } = await createSession({ userId: user.id });
+    const { token } = await createSession({ userId: user.id }, app.clock);

app.clock is systemClock in production, decorated once in services/api/src/plugins/clock.ts. The API's integration tests swap in a TestClock, which is how expiry.e2e.test.ts asserts the X-Session-Expired header without waiting a day. The other six sites are the same substitution in sso-callback.ts, impersonate.ts, logout.ts, touchSession(), revokeSession(), and the worker's job registration. Read one, you have read all seven.

How to check this yourself

verification

Fastest path to seeing the behaviour: run the tests, then hand-expire your own session in the database and watch the browser react.

set up and run the tests
bun install
bun run --cwd packages/db migrate     # applies 0031_session_expires_at

bun test packages/auth/src/__tests__/session.test.ts
bun test services/worker/src/jobs/__tests__/sweep-expired-sessions.test.ts
bun test services/api/src/__tests__/expiry.e2e.test.ts
bun run typecheck                     # proves every SessionResult switch is exhaustive

See the header for yourself. Sign in through the UI, copy the acme_session cookie out of DevTools, then expire the row by hand.

expire it, then call the API
psql "$DATABASE_URL" -c "update sessions set expires_at = now() - interval '1 minute'
                         where user_id = (select id from users where email = 'you@acme.dev');"

curl -i --cookie "acme_session=$TOKEN" http://localhost:3001/api/v1/me
# expect: 401, X-Session-Expired: 1, {"error":"session_expired"}

Then do the same for a session you revoke instead (set revoked_at = now()) and confirm there is no header and the body says unauthenticated. That contrast is the whole point of Chapter 2.

In the browser. With the dev servers running, sign in, leave the dashboard open, run the update above, then click any nav item. Expect exactly one toast and a single redirect to /login?reason=expired with the banner above the form. Several toasts means the handled ref is not doing its job.

Confirm CORS is right. Comment out 'X-Session-Expired' in app.ts, repeat the browser step, and you should get the old silent bounce with no toast. That is the failure mode the line prevents, and curl cannot show it to you.

The sweeper, without waiting 15 minutes: bun run --cwd services/worker job:once -- sweep-expired-sessions, then count rows where expires_at <= now() and revoked_at is null — expect 0 locally. Visual review only: bun run storybook, stories Auth/SessionExpiredToast and Auth/SessionExpiredBanner.
